## 2. Intended vs Actual Architecture

### 2.1 Stated Target Architecture (from CLAUDE.md + mindmap)

```
Hexagonal (Ports & Adapters):
  Driving side: cli.py, api_server.py
  Core: engine.py (Mediator) + engine_core/ (pipeline stages)
  Driven side: api_clients.py, state.py, cache.py

Three Unbreakable Rules:
  1. engine.py = pure Mediator  no business logic
  2. models.py = pure data  no I/O, no asyncio
  3. TDD  test first, always
```

### 2.2 Actual Implementation Reality

**Rule 1  engine.py = Mediator:**  VIOLATED  
`engine.py` is **5,036 lines** with **104 methods** on a single `Orchestrator` class. It contains: LLM call wiring, decomposition logic, evaluation scoring (`_evaluate` = 51 lines), architecture rule generation (`_generate_architecture_rules` = 95 lines), preflight validation (`_run_preflight_check` = 127 lines), telemetry flushing, circuit breaker tracking, and a 289-line `__init__` constructor. The largest single method is `_execute_task()` at **1,247 lines**  larger than most entire services. This is not a Mediator; it is a God Object that has absorbed the entire application layer.

**Rule 2  models.py = Pure Data:**  VIOLATED  
`models.py` imports `asyncio` and contains 4 async methods: `charge()`, `reserve()`, `commit_reservation()`, `release_reservation()`  all on the `Budget` class which belongs to the application layer, not the domain model.

**Rule 3  TDD:**  NOT ENFORCED  
Coverage baseline is `fail_under = 12` (not 80%). The threshold was recently *lowered* from the stated goal: the comment reads `"ratchet: current baseline; raise as more tests are added (target: 50)"`. The stated requirement of 80% has been deferred indefinitely. `_execute_task()`  the most critical method  has no isolated unit tests.

### 2.3 Drift Summary

The codebase shows an intended refactoring (`engine_core/` extraction) that was *started but not completed*. `engine_core/container.py` exists and defines a `ServiceContainer` that would centralize dependency injection for 30+ collaborators  but `engine.py` **does not use it**. The container is dead code from an incomplete migration. The same pattern repeats across the codebase: `application/`, `domain/`, `infrastructure/` subdirectories exist with clean implementations, but the bulk of the code remains in 315 flat files at the top level of `orchestrator/`.

## 5. AI Orchestrator-Specific Review

### 5.1 Agent Orchestration Model
**Design:** 9 specialized agents dispatched by `AgentOrchestrator` in `agents/coordinator.py`.  
**Reality:** `agents/coordinator.py` is 112 lines with a clean `AgentOrchestrator` class  the *declared* entry point. However, the actual execution path goes through `engine.py`, which hardwires `UnifiedClient` calls directly, bypassing the agent layer for core task execution. The agents are a parallel system that doesn't connect to the main pipeline stages in `engine_core/stages/`.

**Verdict:** Two parallel orchestration systems exist that don't speak to each other. The `engine.py` pipeline and the `AgentOrchestrator` appear to operate independently. This suggests the 9-agent system in `agents/` may be aspirational/partially implemented while `engine.py` handles the actual work.

### 5.2 Workflow Coordination
The 7-stage pipeline (`generate  persuasion  critique  evaluate  validate  preflight  self_consistency`) is correctly modeled in `engine_core/stages/`. However, `engine.py`'s `_execute_task()` (1,247 lines) reimplements this pipeline inline rather than delegating to `TaskPipeline` from `engine_core/pipeline.py`. There are **two pipeline implementations**  the one in `engine_core/` (clean, composable, tested) and the one inline in `engine.py` (untested, monolithic).

### 5.3 Message/Event Architecture
`workspace/message_bus.py` implements a publish/subscribe bus  architecturally correct. `hooks.py` implements an `EventType`/`HookRegistry` system. These two event systems overlap in purpose and are not integrated. There is no clear boundary between "workspace events" (file writes, decisions) and "orchestrator events" (task completion, failures).

### 5.4 Context Propagation
Context is propagated through method parameters and `self` state  no explicit context object threading through the pipeline. This is a scalability risk for distributed execution or multi-tenant scenarios. The `PipelineContext` dataclass in `engine_core/pipeline.py` is the right abstraction but it's not used by the live `_execute_task()` path.

### 5.5 Memory/State Boundaries
The 5-layer memory architecture is architecturally sound on paper:
- L1: `ProjectWorkspace` (in-memory)
- L2: `PersistentWorkspace` (SQLite)
- L3: `ExperienceBuffer`
- L4: `KnowledgeGraph` (networkx)
- L5: `AgentCache` (SHA-256 hash + TTL)

However, `engine.py` uses `SQLite` directly (has `import sqlite3`) in addition to the `StateManager` abstraction, meaning persistence can bypass the port layer entirely. The comment `max_parallel_tasks: int = 1  # FIX: Serial execution to avoid SQLite lock` reveals a known concurrency problem with the persistence layer that was resolved with a workaround rather than a fix.

### 5.6 Retry/Failure Semantics
`resilience.py` + circuit breaker logic is implemented. However, 117 swallowed exceptions across 51 files mean that many failure modes are hidden. The `_execute_task()` method catches exceptions silently in several places. Combined with the `except: pass` pattern in `engine.py` (9 occurrences), failure propagation is unreliable.

### 5.7 Concurrency Model
- Max parallel tasks defaulted to **1** (serial execution) due to SQLite locking.  
- `asyncio.Lock()` is instantiated correctly.  
- `asyncio.run()` is called **inside** async functions in `cli_nash.py`  this is a deadlock risk under any async event loop.
- `WeakSet` for background task tracking is a good pattern.

### 5.8 Multi-Agent Scalability
The current in-process single-event-loop model is fundamentally not scalable beyond a single machine. The SQLite state store is a single-writer bottleneck. The 315-flat-file flat namespace means the package cannot be split into independently deployable services without a major restructuring. This is a **hidden monolith**  it looks like a multi-agent system but all agents share one process, one event loop, one database, and one memory space.

## 7. Refactoring Roadmap

### Phase 0  Immediate Fixes (1 week, zero-risk)
1. **Move `Budget` async methods out of `models.py`** into `application/budget_enforcer.py`. `models.py` must be pure data.
2. **Fix `asyncio.run()` inside async context** in `cli_nash.py` (lines 169, 225). Replace with `await` or refactor callers.
3. **Set `fail_under = 40`** in `pyproject.toml` and write tests for `_execute_task()` path. Raise 5% per sprint.
4. **Replace `except: pass` with `except X as e: logger.warning(...)`** in the 9 occurrences in `engine.py`.
5. **Merge `architecture_rules_fixed.py` into `architecture_rules.py`**  stale `_fixed` suffix is dead weight.

### Phase 1  High-Impact Improvements (26 weeks)
1. **Wire `ServiceContainer` into `engine.py`**: The container already exists. Remove the 289-line `__init__` and replace with `container = ServiceContainer.build(...)`. This is the single highest-ROI structural change.
2. **Extract `_execute_task()` into `TaskPipeline`**: This 1,247-line method should become a sequence of `PipelineStage` calls. The stages already exist in `engine_core/stages/`. Delegate to them.
3. **Fix application-layer infrastructure leakage**: Make `application/critique_cycle.py`, `application/evaluator.py`, `application/task_executor.py` depend on `ModelProvider` protocol (from `engine_core/protocols.py`), not `api_clients.UnifiedClient`.
4. **Break the `agents  engine` circular import**: The engine should not import agents; agents should receive a task interface. Define a `TaskDispatch` protocol and inject it.
5. **Consolidate port definitions**: Choose one port system  `domain/ports.py` is cleaner. Deprecate `engine_core/protocols.py` or make it extend the domain ports.

### Phase 2  Structural Reorganization (612 weeks)
1. **Restructure flat files into domain packages**: The 315 flat files group naturally  the analysis above shows clear prefix clusters (`codebase_*`, `app_*`, `context_*`, `meta_*`, `project_*`, etc.). These should become proper sub-packages with `__init__.py` files that define clean public APIs.
   ```
   orchestrator/
    codebase/    # codebase_*.py  7 files
    appbuilder/  # app_*.py  6 files
    context/     # context_*.py  6 files
    meta/        # meta_*.py  6 files
    project/     # project_*.py  6 files
    git/         # git_*.py  5 files
   ```
2. **Replace SQLite single-writer with async-safe persistence**: Either use `aiosqlite` with WAL mode and connection pooling (already partially done) or migrate to PostgreSQL/DuckDB for concurrent writes. Remove the `max_parallel_tasks=1` workaround.
3. **Unify the two pipeline systems**: Make `engine.py._execute_task()` call `TaskPipeline` from `engine_core/`. Remove the inline reimplementation.
4. **Unify the two event systems**: Choose between `workspace/message_bus.py` and `hooks.py`. Standardize on one event bus.

### Phase 3  Long-Term Architecture Evolution (36 months)
1. **Split into independently deployable services**: Once the flat file structure is resolved and domain boundaries are clean, extract the agent system into a separate process/service with a message queue (Redis Pub/Sub or NATS) as the event bus.
2. **Replace structlog (1 user, 0% adoption)**  or mandate it. Pick one logging standard.
3. **Add distributed tracing**: Wire `tracing.py` (`Tracer`) through the pipeline as a `LoggingProvider` protocol implementation. Every LLM call should emit a trace span.
4. **Introduce contract tests**: For each `Protocol` interface in `domain/ports.py`, write a contract test suite that every adapter must pass. This ensures future LLM provider integrations can't silently violate the contract.

## Final Verdict

The AI Orchestrator has **excellent architectural ambition** documented in its mindmap and CLAUDE.md. It has a sound conceptual design: hexagonal architecture, 7-stage pipeline, protocol-first ports, DI container. Several modules (`domain/`, `infrastructure/`, `engine_core/stages/`, `agents/`) show what the codebase can look like when the architecture is respected.

The fundamental problem is that **the refactoring was never completed**, and organic feature growth continued into the flat namespace while the structured subsystems were left half-wired. The result is two parallel systems (one clean, one monolithic), 315 ungoverned flat files, and a God Object at the center that has absorbed logic that was supposed to live in the extracted layers.

The system is currently **maintainable only by its original author**. The path forward requires completing the already-declared `ServiceContainer` migration, extracting `_execute_task()` into the pipeline framework that already exists, and restructuring the flat files into the domain packages that the prefix analysis already reveals naturally.

**This is a fixable problem**  the foundations are sound and the target architecture is well-understood. The work is organizational and surgical, not conceptual.
