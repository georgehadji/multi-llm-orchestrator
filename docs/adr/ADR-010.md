# ADR-010: State Store Scaling Strategy

**Date:** 2025-07-21
**Status:** Accepted

## Context

The orchestrator's state is persisted via `StateManager` (`infrastructure/state.py`), which uses a single `aiosqlite` connection to a SQLite database at `~/.orchestrator_cache/state.db`. Each project run checkpoint writes to this database. Under concurrent project execution, write contention on the single-file database becomes the bottleneck.

This ADR documents the current capacity, short-term mitigations, medium-term replacement, and long-term evolution of the state persistence layer.

### Current Architecture

- SQLite via aiosqlite, WAL journal mode, single-file
- One `StateManager` instance per `Orchestrator` (stateful)
- `ProjectState` serialized as JSON blobs (checkpoints, circuit-breaker state, resume tokens)
- 10-entry checkpoint retention per project
- Single-writer, multiple readers (WAL mode allows concurrent reads during writes)

### Constraints

1. **No external infrastructure** — the orchestrator must work with zero configuration beyond API keys
2. **Resumability** — crash recovery requires reading the last-known-good state after restart
3. **Concurrent projects** — users may run multiple orchestrator instances (e.g., CLI + dashboard)

## Decision

### Short-term (v6.x — current): Connection pooling + read replicas

SQLite WAL mode supports multiple concurrent readers while a single writer is active. The current implementation uses a single connection. We can improve throughput without architectural changes:

| Tactic | Effort | Throughput Gain |
|--------|--------|----------------|
| Connection pooling (one writer + N readers) | 2 days | ~3× for read-heavy workloads |
| WAL checkpoint tuning (`PRAGMA wal_autocheckpoint=1000`) | 0.5 days | ~2× for write-heavy workloads |
| Batch writes (aggregate checkpoints over 500ms window) | 1 day | ~5× for bursty write patterns |
| Separate state DB per project (namespaced files) | 1 day | ~N× for N concurrent projects |

**Implemented:** None yet. These are available on demand when concurrent-project usage exceeds 5 simultaneous runs.

### Medium-term (v7.x): Abstract `StatePort` with PostgreSQL adapter

The `StatePort` protocol already exists in `domain/ports.py`. Adding a PostgreSQL adapter (`StatePort` → `psycopg3`/`asyncpg`) gives:

- True concurrent writes via MVCC
- Shared state across orchestrator instances (horizontal scale)
- Rich query capabilities (project search, analytics, cost tracking by team)

**Migration path:**
1. Implement `PostgresStateManager` implementing `StatePort`
2. Feature-flag: `ORCH_STATE_BACKEND=sqlite|postgres`
3. Dual-write during transition (write to both, read from primary)
4. Drop SQLite after validation

**Trade-off:** Requires PostgreSQL 14+ instance (can be ephemeral via Docker, or managed).

### Long-term (v8.x): Event-sourcing with append-only event log

Replace mutable state with an append-only event log. Project state is derived by replaying events. This is the most scalable but highest-effort option:

| Benefit | Cost |
|---------|------|
| Zero write contention (append-only) | ~2× storage for event log |
| Full audit trail (every state change recorded) | Event replay latency at startup |
| Multiple orchestrator instances from same log | Schema evolution complexity |
| Time-travel debugging (reconstruct state at any point) | Event schema must be forward-compatible |

**Implementation sketch:**
```
EventStore (append-only log)
  → Event types: ProjectStarted, TaskStarted, TaskCompleted, TaskFailed,
                  BudgetUpdated, CircuitBreakerTripped, ...
  → EventBus publishes each event to both the store (for persistence)
    and live subscribers (for real-time dashboards)
  → ProjectState = fold(events, seed_state)
```

## Consequences

### Positive
- [SHORT-TERM] Zero code changes needed today — existing SQLite scales to ~5 concurrent projects
- [MEDIUM-TERM] PostgreSQL adapter gives true horizontal scaling without changing the port interface
- [LONG-TERM] Event-sourcing enables audit, replay, multi-instance, and time-travel debugging
- All options use the existing `StatePort` protocol — no application-layer changes needed

### Negative
- [MEDIUM-TERM] PostgreSQL adds deployment dependency (can be mitigated with containerized PG for development)
- [LONG-TERM] Event-sourcing requires careful schema design — event types are immutable once consumed
- Migration from SQLite → PostgreSQL requires a data migration script

### Neutral
- The event-sourcing approach overlaps with the existing `EventBus` architecture — events are already published, they just aren't persisted yet
- Partial event-sourcing (persist events but keep SQLite for snapshots) is a viable intermediate step

## Capacity Targets

| Metric | Current (SQLite, single conn) | Short-term (pooling) | Medium (PostgreSQL) | Long-term (event-sourcing) |
|--------|------------------------------|---------------------|--------------------|---------------------------|
| Concurrent projects | ~3-5 | ~15-20 | ~100+ | ~1000+ |
| Checkpoint latency (p95) | ~50ms | ~15ms | ~5ms | ~2ms (append-only) |
| Startup time (resume, 100 tasks) | ~200ms | ~100ms | ~50ms | ~500ms (replay) |
| Deployment dependency | None | None | PostgreSQL 14+ | PostgreSQL 14+ + event schema |
