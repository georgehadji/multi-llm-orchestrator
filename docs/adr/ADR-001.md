# ADR-001: Hexagonal Architecture with Protocol-based Ports

**Date:** 2026-05-27
**Status:** Accepted

## Context

The orchestrator's core modules (engine.py, models.py) had become tightly coupled
to concrete infrastructure implementations (api_clients.UnifiedClient, SQLite).
This made testing impossible without API keys and prevented swapping implementations.

## Decision

Adopt hexagonal (ports & adapters) architecture:

- **Domain layer** (`domain/ports.py`) — defines abstract interfaces as `typing.Protocol`
- **Application layer** (`application/`, `engine.py`) — depends on Protocols only
- **Infrastructure layer** (`infrastructure/`, `api_clients.py`) — implements Protocols

All Protocols use `@runtime_checkable` for `isinstance()` validation in tests.

## Consequences

- Application files no longer import `UnifiedClient` directly (use `LLMClient` protocol)
- Tests can use `NullCache`, `NullState`, `NullEventBus` — no infrastructure needed
- Each Protocol has a contract test suite (`tests/contracts/test_*_port.py`)
- Adding a new LLM provider requires implementing the Protocol, not modifying engine.py

# ADR-002: ServiceContainer as DI Wiring Layer

**Date:** 2026-05-27
**Status:** Accepted

## Context

`Orchestrator.__init__` had grown to 305 lines, manually wiring 50+ collaborators
with inline constructor calls. This was fragile, untestable, and duplicated between
engine.py and tests.

## Decision

Extract all wiring into `ServiceContainer` (`engine_core/container.py`):
- `ServiceContainer.build()` is a single factory method
- `Orchestrator.__init__` accepts `container: ServiceContainer | None = None`
- Circular dependencies (executor needs `_execute_task`) resolved via `wire_executor()`

## Consequences

- `Orchestrator.__init__` reduced from 305 to 159 lines
- Tests can create an orchestrator with mocked services in one line
- Wiring changes are centralized in `ServiceContainer.build()`
- Service container has one canonical factory — no ad-hoc wiring

# ADR-003: Pipeline Runner as Execution Abstraction

**Date:** 2026-05-27
**Status:** Accepted

## Context

`_execute_task` was a 1,200-line method containing all pipeline logic (generate,
critique, revise, evaluate) inline. It was untestable, unreviewable, and coupled
every stage to engine.py.

## Decision

Extract the 7-stage pipeline into `engine_core/stages/` with a `TaskPipeline`
coordinator.  `_execute_task` delegates to `self._pipeline.run(ctx)` in 19 lines:
- `PipelineContext` carries task + model + state through all stages
- Each stage is a separate class with a single responsibility
- `PipelineRunner` handles topological sort and parallel execution

## Consequences

- `_execute_task` reduced from ~1,200 to 19 lines
- New stages can be added without touching engine.py
- Pipeline stages are independently testable
- `PipelineContext` provides a clear data contract between stages

# ADR-004: max_parallel_tasks = 3 (SQLite WAL Mode)

**Date:** 2026-05-27
**Status:** Accepted

## Context

The original `max_parallel_tasks = 1` was a workaround for SQLite lock contention.
WAL mode was enabled but not leveraged, and the single connection bottlenecked
all parallel operations.

## Decision

- Raise `max_parallel_tasks` from 1 to 3
- Add 5-connection pool to StateManager
- Verify WAL mode already active (PRAGMA journal_mode=WAL)
- Benchmark before increasing further

## Consequences

- 3× throughput for parallel task execution
- WAL mode supports concurrent readers without locking
- Connection pool prevents single-connection bottleneck
- Future increases to 10+ need benchmark data first

# ADR-005: EventBus Unification

**Date:** 2026-05-27
**Status:** Accepted

## Context

Two separate event systems existed: `workspace/message_bus.py` (inter-agent
messaging) and `events/hooks.py` (orchestrator lifecycle hooks). They had
overlapping purpose but incompatible APIs.

## Decision

Merge both into a single `events/core.py`:
- `EventBus` extends both `HookRegistry` and `AgentMessageBus`
- Lifecycle hooks use synchronous fire-and-forget (for CLI output, progress bars)
- Agent messaging uses async publish/subscribe with per-agent inboxes
- Both legacy files become backward-compat shims

## Consequences

- One canonical event system instead of two
- No ambiguity about which event system to use for new features
- Backward compatibility preserved via re-export shims
- EventType enum + MessageType enum scoped in one file

# ADR-006: Budget Moved from models.py

**Date:** 2026-05-27
**Status:** Accepted

## Context

`Budget` class in `models.py` had async methods (`charge()`, `reserve()`,
`commit_reservation()`, `release_reservation()`) with `asyncio.Lock` — violating
the rule that `models.py` = pure data with no I/O or async.

## Decision

Move `Budget` class and `BUDGET_PARTITIONS` to `orchestrator/budget.py`:
- `models.py` retains a re-export import for backward compatibility
- `ProjectState.budget: Budget | None` imports from `budget.py`
- `models.py` no longer imports `asyncio`

## Consequences

- `models.py` is now pure data (no async, no I/O)
- `budget.py` properly lives in the application layer
- All existing imports (`from .budget import Budget`) already worked
- Backward compat via `from .budget import Budget` in models.py
